# Scenes, progress block and the debug warp (phase 2)

Debug tool: `tools/debug/warp.lua` + the scene list `tools/debug/scenes.gba.txt` (generated by
`tools/debug/gen_scenes.py`; edit that). One scene: AGENTS.md "Warp". All of them, from cold boot, in parallel:
`python -X utf8 tools/debug/warp_all.py [NAME|GLOB ..] [--rom work/orig.gba] [--states]` (`--states` regenerates
`work/states/<name>.mss`). Recon helpers: `tools/scenecalls.py` (every constant scene transition),
`tools/constrefs.py` (code loading given constants, e.g. a BG screen index), `tools/lua/scenelog.lua` (scene log +
raw jump), `tools/lua/scenewrites.lua` (who writes a scene id).

## Scene machine (verified: main loop disassembly, every warp in the scene list)

- Main loop 0x08000300 calls the dispatcher **0x08026684** once per frame. State block **0x030052F0**:
  +0 scene, +1 sub-state, +2 u16 timer/step, +4 last return code, +5 call depth, +6/+7 next scene/sub,
  +0x10/+0x14/+0x18 call stack (scenes, subs, timers). Handler table **0x08D22CA0** (u32 Thumb pointers, by scene).
- A handler returns 0x80 (stay), 0x81 (sub+1), 0x82 (goto +6/+7), 0x83 (call: push, goto), 0x84 (return).
  Helpers: 0x08026794 goto(scene<<8|sub), 0x080267A8 call, 0x080267BC call and advance own sub, 0x080267DC call
  with an explicit return point. Scenes 128 (fade out), 129, 144 (fade in) are called helpers.
- Each scene handler copies a sub-state table to the stack and calls `table[sub]`.

## Warp mechanics

`warp.lua` presses Start through the logos and title, and at the first dispatcher call with the top menu up
(scene 0 sub 4, depth 0) writes the entry's pokes and sets scene/sub. Entering a stage through the map
(scene 2 sub 0) with F58 = 1 and the *previous* stage poked makes the game itself advance, show the area card
when the area changes, run character select, load the stage and its event, as in play. A direct jump to scene 4
skips the stage load (empty level, instant clear), so the list never does that.
Cheats (entry options, see gen_scenes.py): `@clear[N]` jumps the play loop (scene 4 or 13 sub 16) to sub 80 after
90 frames, N times, and drives the points screen and the save menu to "next stage"; `@subN` jumps once to sub N;
`@pause`; `@hold`. `--var GOD=1` pins the player's HP (u16 **0x03005264**, verified: 16 -> 11 under hits without
it, held at full with it; 0xFFFE until the stage sets it). Mesen randomises save memory, so run lengths vary by a few hundred frames between runs: the
scene list's frame budgets have slack.
With `@clear`, sub 81 gets two helpers (warp.lua): **unstick** (a walk that stalls 30 frames against a wall:
x += 16 px) and **TIMEOUT81** (900 static frames: goto scene 5/6 as sub 82 would). Both are logged. Three
post-clear events hang the CPU after a forced clear (loop in IWRAM 0x030011C8-0x0300121C, dispatcher no longer
called, found with `tools/lua/pcsample.lua`): 2-4 and 3-4 (no dialogue yet) and 4-1 (after its dialogue). Likely
they wait on the stage boss, which a clear 90 frames in never spawns. Their remaining lines need a boss-fight
route (GOD + reaching the boss) if phase 8 text coverage finds them unreached.
After TIMEOUT81, 2-4 and 3-4 reach the summon (scene 5), which stays frozen on a still. 4-4's event ends
normally but its summon waits in scene 5 sub 16 for good; 0x03001F58 stays 01 there, while the working 1-4 run
has 09. The area battles themselves are covered by the `battle_N` entries.
CLEAR! banner: boss stages (x-4) have none, since sub 80 passes straight to 81. Other stages show it for ~30
frames at the end of sub 80, so 60-frame shots can miss it. The forced clears of 3-1 and 5-1 never draw it
(checked with shots every 20 frames): the clear lands mid-fight, the HUD drops and the camera pans off.
The top menu is a ◀ item ▶ carousel showing one item at a time.

## Event scripts and the message viewer (phase 8, verified)

Event script 3.N is loaded by the resource loader 0x080202E8 with r0 = 0xC300 + N and **r1 = entry slot**
(`tools/lua/evlog.lua`): stage start 0x0802961D -> slot 0, post-clear 0x0802BB29 -> slot 1; the title loads
0xC31F (attract). Each script has 16 u32 self-relative slot offsets; 64 = empty. Non-empty mid-stage slots (2-15)
exist in 3.1, 3.4, 3.6, 3.8, 3.9, 3.14, 3.15, 3.17, 3.19, 3.21-3.24 (boss arrivals and the like); forcing one in
place of slot 0 (`warp.lua --var EVSLOT=k [EVSCRIPT=n]`) runs it without its stage state, so no dialogue shows
(1-4 slot 3: player dies in a loop). Script 3.15 (an "empty" stage slot) has a slot 6 and text table s22 holds 9
real lines (summon/truck), but nothing loads 3.15 in play.

Text reaches the screen through three loader calls with group 2 (id 0x8200 + table, r1 = message slot):
the preprocessor's include code 0x14 (0x08007648), the 0xF0-0xFF bytecode interpreter at 0x0800A320 (opcode 0xFD,
handler 0x0800A7B0, table from its 4th argument byte) and the **event dialogue command at 0x080214A8** (r7 = table,
r4 = slot). The table index is master entry - 1 (s08 = 11). Over the 75-scene tour, master entries 1 (s00),
6 (s04), 7 (s05) and 8 (s06) were never read (`tools/lua/masterread.lua`: every read comes from 0x08020332-40).

**Message viewer** (`tools/lua/msgview.lua`, runner `tools/msgview_run.py`): stage 1-1's intro runs 32 event
text commands; the probe replaces the n-th command's (r7, r4) with the n-th pair of `MSGS='t:s,..'`, and
warp.lua's `ADVANCE=40` pages through them. So any message can be drawn in the real dialogue window from a cold
boot, which covers lines that only boss fights or unreachable scripts show.
